# Поинтвайзный первый этап: что изменилось

Первый этап (бинарные маркеры) переведён с пары на один ответ: в промт подаётся ровно одна «моделька». Всё остальное — словарь маркеров, калибровка, сканы, кросс-проверки — взято из `tov_binary_markers_v2.md` без изменений, чтобы разница между прогонами была только в схеме подачи, а не в правилах разметки.

Файлы:

- `prompts/tov_binary_markers_pointwise.md` — промт;
- `sql/markers_pointwise_input.sql` — сборка инпута (две строки на пару);
- `sql/markers_pointwise_collapse.sql` — схлопывание обратно в одну строку.

## Промт

Диф относительно v2 — четыре точки, всё остальное посимвольно совпадает:

1. **SYSTEM_ROLE.** Добавлен абзац «тебе подаётся РОВНО ОДИН ответ»: нет сравнения, нет победителя, нет упоминаний «другого ответа». Отдельно сказано, что оценка абсолютная — нельзя двигать порог маркера, ориентируясь на воображаемую альтернативу.
2. **Блок 3.** Из заголовка убрано «отдельно для каждого ответа» — сканы теперь по определению одни.
3. **Блок 5.** Плоская структура вывода: три ключа верхнего уровня — `analysis`, `scan`, `markers`. Префиксы `model_1_*` / `model_2_*` убраны, требование «все 13 маркеров» осталось.
4. **Входные данные.** Один плейсхолдер `{{model_answer}}` вместо `{{model_1_answer}}` / `{{model_2_answer}}`.

Плюс одно новое напоминание в конце: «плохое вступление в отличном ответе — всё равно `bad_intro`». Это защита от специфически поинтвайзного дрейфа, когда общее впечатление от ответа начинает подменять пороги отдельных маркеров.

## Зачем

- **Нет позиционного эффекта.** В пайплайне пара гоняется прямым и обратным порядком именно потому, что джадж по-разному относится к первому и второму ответу. Для маркеров этот костыль больше не нужен: ответ в задании один, переставлять нечего.
- **Нет перетекания разметки.** В парном промте маркеры второго ответа регулярно калибруются «на фоне» первого — а маркер бинарный и абсолютный, фон в него заходить не должен.
- **Короче контекст.** В задании один ответ вместо двух при том же объёме правил: сканы (Блок 3) реально выполняются, а не сворачиваются под давлением длины.

Цена — вдвое больше вызовов инфера на первом этапе.

## SQL

**Было:** одна строка = пара, одна колонка `infer_dialog`, промт с двумя ответами.

**Стало:**

1. `markers_pointwise_input.sql` — `FLATTEN LIST BY` по `AsList(1, 2)` разворачивает каждую исходную строку в две с колонкой `answer_slot`. В `infer_dialog` уходит `answer_1` при `answer_slot = 1` и `answer_2` при `answer_slot = 2`. Инфер гоняется один раз по колонке `infer_dialog`, как и раньше, — просто строк вдвое больше.
2. `markers_pointwise_collapse.sql` — парсит `dst` (тот же `process_json`, что и в склейке: срезает ```json-обёртку и мусор по краям), делит строки по `answer_slot` и джойнит их обратно по `instruct_id`. На выходе снова одна строка на пару с `ext_markers_1` / `ext_markers_2` — ровно в том виде, в каком их читает `judge_merge_pretty.sql`. Дополнительно кладутся `ext_scan_1/2` и `ext_analysis_1/2` (сканы и разбор интента — полезно при разборе расхождений с золотом) и флаг `markers_parsed_ok`.

`judge_merge_pretty.sql` править не нужно: он берёт `ext_markers_1` / `ext_markers_2` из прямой таблицы, а после схлопывания они лежат там же и означают то же самое — первый относится к `answer_1`, второй к `answer_2`.

Джойн в схлопывании — INNER: пара, у которой не доехала одна половина, из выборки выпадает. Это осознанно: недоехавший инфер иначе превратился бы в «все маркеры false», то есть в тихую ошибку метрики. Расхождение числа строк до и после видно счётчиком.

## Что проверить на первом прогоне

- Число строк после `markers_pointwise_input.sql` — ровно вдвое больше исходного.
- `markers_parsed_ok = false` — доля строк, где джадж отдал невалидный JSON; в парной схеме такие случаи били сразу по обоим ответам, здесь — только по одному.
- Метрики маркеров против золота в сравнении с парным прогоном: смысл замены именно в том, чтобы recall по «чувствительным» маркерам (`stuffy_bureaucratic`, `over_emotional`, `language_errors`) не проседал из-за длины контекста.
